## 0. このドキュメントについて

本書はこのプロダクトの**正式な仕様書**であり、「何を作るのか／なぜ作るのか」の唯一の正とします。

### 0-1. ドキュメントの役割分担

| ドキュメント | 答える問い | 主な読者 | 書かないこと |
|---|---|---|---|
| `README.md` | これは何か／どう起動するか | 初見の人・新規参画者 | 仕様の詳細（本書へリンクする） |
| **`docs/SPECIFICATION.md`（本書）** | **何を作るのか／なぜ作るのか** | 企画・PO・実装者全員 | ライブラリ名・ファイルパス・コード |
| `docs/DESIGN.md` | どう作るのか（技術設計） | 実装者 | 仕様判断そのもの |

### 0-2. 運用ルール

1. **本書と `DESIGN.md` が矛盾した場合、本書を正とする。** `DESIGN.md` 側を修正する
2. **1つの事実は1箇所にだけ書く。** 他のドキュメントからは参照（リンク）する
3. 仕様変更は本書を先に更新し、その後に設計・実装を追随させる
4. 本書は実装技術に依存しない。特定のライブラリ・フレームワーク・ファイル構成を前提としない

### 0-3. 記法

- **MUST** — 必須。満たさない実装は仕様違反
- **SHOULD** — 推奨。逸脱する場合は理由を記録する
- **MAY** — 任意
- 各章末の「受け入れ基準」は、その章が実装完了したと判断するための確認項目

## 1. プロダクトの目的

### 1-1. 一文定義

> 社員が業務を進める際に、**次に何をすればよいか迷わず**、必要な情報・ツール・タスク・期限が
> 適切なタイミングで提示され、**業務を最後まで完遂できる**状態をつくるプラットフォーム。

### 1-2. これは何ではないか

**本プロダクトはAIチャットツールではありません。** これは方針ではなく制約です。

- AIチャット画面をメインUIにしては **MUST NOT**
- ユーザーが「AIに質問して答えを得る」ことを主要導線にしては **MUST NOT**
- AIは文章生成・業務分解・不足情報検出・検索結果整理・影響分析などの**補助**に限定する

主役は「業務」であり、AIではありません。

### 1-3. システムが提示すべき7要素

ユーザーが業務を開始したとき、システムは以下を適切なタイミングで提示 **MUST**：

| # | 要素 | 答える問い |
|---|---|---|
| 1 | 現在の状況 | 今どこにいるのか |
| 2 | 次にやること | 次は何をすればいいのか |
| 3 | 必要な情報 | 何を見ればいいのか |
| 4 | 関連するルール | 今回は何に注意すべきか |
| 5 | 派生タスク | この変更で他に何が必要か |
| 6 | 期限 | いつまでにやればいいのか |
| 7 | 必要なツール | どの機能を使えばいいのか |

### 1-4. 成功の定義

ユーザーが以下を**考える時間がゼロに近づく**こと。

「何をすればいい？」「次は何だっけ？」「この変更って他に何か対応必要？」
「いつまでにやればいい？」「どこに書いてあった？」「誰に確認すればいい？」

## 2. 解決する課題

| # | 課題 | 現状で起きていること | 本プロダクトの解 |
|---|---|---|---|
| 1 | 情報を探す時間が長い | マニュアル・Drive・Slack・過去メールを横断して探す | STEPに紐付いたナレッジを**その場に**出す（§16） |
| 2 | 次に何をするか分からない | 経験者に聞く／止まる | 業務ナビゲーターが現在STEPと次を明示（§6） |
| 3 | 業務手順が属人化している | 「あの人しか分からない」業務が残る | 業務フローをデータとして共有資産化（§7） |
| 4 | 手順漏れが起きる | チェックリストが個人管理・形骸化 | 完了条件を満たさないと次STEPへ進めない（§7-6） |
| 5 | 派生タスクが漏れる | 変更したが関連対応を忘れる | 変更を起点に派生タスクを自動提案（§10） |
| 6 | 変更の影響を見落とす | 何に波及するか誰も全体を把握していない | インパクトマップで直接・間接影響を可視化（§12） |
| 7 | 一時的なルールを覚えられない | 「今月だけ」の指示が徹底されない | 期間限定ルールが該当STEPに自動反映（§14） |
| 8 | 締切から逆算できない | 気づいたら間に合わない | ゴール期限から各作業の期限を逆算提案（§13） |

### 2-1. 測定指標（将来の効果検証用）

- 業務開始から完了までのリードタイム
- STEP完了率（途中放棄率）
- 派生タスクの提案受諾率／後から手動追加されたタスク数
- 期限超過タスク比率
- ナレッジの検索経由アクセス比率（**低いほど良い** — 探させていない証拠）

## 3. ユーザー像

### 3-1. ロール

| ロール | 呼称 | 主な関心 | 利用頻度 |
|---|---|---|---|
| **実行者** | 現場担当者（営業・インサイドセールス等） | 目の前の業務を漏れなく早く終わらせたい | 毎日 |
| **業務設計者** | 管理者・マネージャー | 業務手順を標準化し、属人化を解消したい | 週数回 |
| **観測者** | マネージャー・経営 | 進捗と滞留を把握したい | 週数回 |

同一人物が複数ロールを兼ねることを想定 **MUST**（例：マネージャーが実行者でもある）。

### 3-2. 主要ペルソナ

**P1. 実行者：入社1年目の営業担当**
- 状況：問い合わせ対応の手順が完全には頭に入っていない。過去メールを探す時間が長い
- 期待：業務を開くと手順が出て、テンプレも情報もその場にあり、迷わず完了できる
- 失敗体験：「必須確認項目を聞き忘れて再度連絡する羽目になった」

**P2. 業務設計者：営業企画/マネージャー**
- 状況：新しい施策のたびに「今月はこれも確認して」とSlackで周知するが徹底されない
- 期待：フローに組み込めば全員が自動的に従う状態にしたい。**コードを書かずに**
- 失敗体験：「周知したのに半分の担当者が実行していなかった」

**P3. 観測者：部門長**
- 状況：どの業務が止まっているか、変更の影響が消化されたかが見えない
- 期待：滞留と影響範囲が一覧で分かる

### 3-3. 非対象ユーザー（v1.0時点）

- 社外ユーザー（顧客・パートナー）— 将来検討
- 開発者以外による業務部品そのものの追加 — 部品追加は開発作業とする（§28-4）

## 4. 基本UX

### 4-1. 中心原則

> **ユーザーは機能を選ばない。業務を開くと、その場に必要な機能が出てくる。**

「メール機能を使う」「タスク機能を使う」「ナレッジを探す」という操作をさせては **MUST NOT**。
「今の業務で次に必要な作業」を提示し、その中に機能を埋め込みます。

### 4-2. 情報の提示優先順位

画面上の視覚的優先順位は、常に以下の順序 **MUST**：

```
1. 今何をしているか      ← 最も目立たせる
2. 次に何をするか
3. いつまでか
4. 注意事項（ルール）
5. 必要な情報（ナレッジ）
6. 必要なツール
```

### 4-3. 常に答えられていること

ユーザーがどの画面にいても、以下3つが**スクロールせずに**分かる **MUST**：

1. 自分は今どの業務のどのSTEPにいるか
2. 次に押すべきボタンはどれか
3. いつまでに終わらせる必要があるか

### 4-4. 起点は常に「業務」

- ログイン直後の起点は **HOME**（今日やることの一覧）
- HOMEから業務を開始・再開すると **業務ナビゲーター** に入る
- 業務ナビゲーターが滞在時間の最も長い画面になることを想定する

### 4-5. 受け入れ基準

- [ ] 主要12画面のいずれにも、AIチャット入力欄が主役として配置されていない
- [ ] HOMEを開いてから「今日やること」を認識するまでにスクロール不要
- [ ] 業務ナビゲーターで、現在STEPが他のSTEPより明確に視覚的優位にある

## 5. 情報を探させないための設計思想

本プロダクトの中核思想です。以下4原則を全画面に適用 **MUST**。

### 原則1：文脈で出す（Push, not Pull）

情報は「探しに行くもの」ではなく「出てくるもの」とする。
STEPが必要とする情報は、そのSTEPを開いた時点で画面上に存在していなければならない。

### 原則2：検索を主導線にしない

ナレッジ検索・テンプレ検索・企業検索の「検索画面」は存在してよいが、**それが主導線であってはならない**。
主導線は常に「業務STEPからの提示」とする。検索は取りこぼしを拾う補助手段。

### 原則3：全部見せない（スコープ限定）

現在の業務・STEPに関係するものだけを表示 **MUST**。

| 状況 | 表示するもの | 表示しないもの |
|---|---|---|
| 企業検索STEP | 企業検索に関するルール・ナレッジ | メール関連ルール、他業務のルール |
| メール作成STEP | メール関連ルール・テンプレ・差し込み情報 | 企業検索ルール、無関係なナレッジ |

**ルール一覧を全件表示する画面は管理画面のみ** とし、業務実行中には出さない **MUST NOT**。

### 原則4：その場で完結させる

情報を見つけた後に別画面へ移動させない。
STEP内で「見る → 判断する → 実行する → 完了する」が完結すること。

### 5-1. コンテキストスコープの定義

「現在のSTEPに関係するもの」は以下の規則で決定 **MUST**：

| 種類 | 表示条件 |
|---|---|
| ルール | STEPのルールタグ ∩ ルールの適用対象タグ が空でない、かつ適用期間内 |
| ナレッジ | STEPが明示参照している、または業務部品の種別が一致する |
| 不足情報 | STEPまたは業務の完了条件から機械的に導出された未充足項目 |
| 派生タスク | この業務／STEP由来のもののみ |
| ツール | STEPの業務部品が必要とする外部連携のみ |

### 5-2. 受け入れ基準

- [ ] 任意のSTEPで表示されるルール件数が、全ルール件数より確実に少ない
- [ ] 表示された各ルールについて「なぜ今これが出ているか」を追跡できる
- [ ] STEP実行中に別画面へ遷移せずに完了できる（企業検索・メール作成含む）

## 6. 業務ナビゲーター

業務実行中の**中心画面**であり、本プロダクトで最も重要な画面です。

### 6-1. 画面の責務

進行中の業務について「現在地・次の行動・必要な材料」を一画面で提示し、業務完遂まで導く。

### 6-2. 必須表示要素

```
┌──────────────────────────────────────────────────────────┐
│ 株式会社○○ ／ CV後対応              STEP 3 / 6  期限 9/12 │← 現在地
├────────────┬──────────────────────────┬──────────────────┤
│ ✓ 顧客情報確認│                          │ ⚠ このSTEPのルール │
│ ✓ ヒアリング  │   ★ メール作成           │ 📄 関連ナレッジ    │
│ → メール作成  │   （現在STEPの部品UI）   │ ❗ 不足情報        │
│ ○ 資料送付    │                          │ 🔀 派生タスク      │
│ ○ フォロー設定│                          │ ⏱ 期限            │
│ ○ 完了        │                          │ 🔧 必要ツール      │
├────────────┴──────────────────────────┴──────────────────┤
│ 次にやること：お礼メールを作成して送信する      [ 完了して次へ ] │
└──────────────────────────────────────────────────────────┘
```

| 要素 | 要件 |
|---|---|
| 業務ヘッダー | 対象（顧客/案件名）・業務名・進捗（n/N）・期限 **MUST** |
| STEPレール | 全STEPと状態を一覧。現在STEPを最も強調 **MUST** |
| 現在STEP領域 | 画面内で最大面積・最高コントラスト **MUST** |
| コンテキストパネル | §5-1のスコープ規則に従う **MUST** |
| 次アクション帯 | 「次にやること」を**1文**で明示＋主要CTAボタン **MUST** |

### 6-3. STEPの状態

| 状態 | 記号 | 意味 |
|---|---|---|
| `done` | ✓ | 完了済み |
| `active` | → | 現在実行中（複数同時可） |
| `pending` | ○ | 未着手 |
| `skipped` | – | 条件により飛ばされた |
| `blocked` | ⛔ | 依存または不足情報により実行不可 |

### 6-4. 操作

| 操作 | 挙動 |
|---|---|
| 完了して次へ | 完了条件を検証 → 満たせば次STEPへ遷移。満たさなければ不足を明示して留まる |
| 戻る | 完了済みSTEPを再度開き、内容を修正できる。修正は変更イベントとして記録（§10） |
| 中断 | 状態を保存して離脱。HOMEの「進行中の業務」から再開できる **MUST** |
| スキップ | 任意STEPのみ可。理由の記録を必須とする |
| 業務を中止 | 理由を記録して終了。派生タスクの扱いをユーザーに確認する |

### 6-5. 並列STEP

業務は一本道とは限りません。複数STEPが同時に `active` になり得ます **MUST**。
その場合、STEPレールで並列であることを視覚的に示し、次アクション帯には
「今すぐ着手できるSTEP」のうち期限が最も近いものを提示 **SHOULD**。

### 6-6. 受け入れ基準

- [ ] 画面を開いた瞬間、現在STEPがどれか2秒以内に分かる
- [ ] 「次にやること」が常に1文で表示されている
- [ ] 完了条件未達で「完了して次へ」を押すと、何が足りないか具体的に表示される
- [ ] 中断して再訪すると、離脱時と同じSTEP・同じ入力内容が復元される

## 7. 業務フロー

### 7-1. 最重要制約

> **業務フローをコードにハードコードしては MUST NOT。**
> 業務フロー・STEP・順序・条件分岐・ルール・タスク生成・期限・依存関係は
> **すべてデータとして** 管理し、コード変更なしに追加・変更できること。

個別業務専用のシステムを作ってはなりません。

### 7-2. 業務の2種類

| 種類 | 説明 | 例 |
|---|---|---|
| **定型業務** | あらかじめ手順が定義された業務 | 新規問い合わせ対応、CV後対応、企業リサーチ、商談準備、展示会フォロー |
| **アドホック業務** | 突発的に発生し、その場で手順を組み立てる業務（§8） | 「来週までに提案資料を作って」 |

### 7-3. 定義と実行の分離

| 概念 | 役割 |
|---|---|
| **業務フロー定義** | 手順のテンプレート。管理者が作成・編集する |
| **業務実行** | 定義から生成された、進行中の一件一件の業務 |

**業務実行は、開始時点の定義バージョンを固定 MUST。**
管理者が定義を編集しても、進行中の業務は影響を受けません。新しい定義は次回の開始分から適用されます。

### 7-4. 業務フロー定義が持つ情報

| 項目 | 必須 | 説明 |
|---|---|---|
| 識別子 | ✓ | 人が読める安定した識別子 |
| バージョン | ✓ | 発行のたびに増加 |
| 状態 | ✓ | 下書き／公開中／アーカイブ |
| 業務名・説明 | ✓ | |
| 対象者 | | ロール・チーム |
| 起動条件 | ✓ | 手動／タスクから／外部イベント／スケジュール |
| STEP群 | ✓ | §7-5 |
| STEP順序・分岐 | ✓ | §7-6 |
| 変数定義 | | 業務中に扱うデータの型・必須有無 |
| 完了条件 | ✓ | §7-7 |
| 期限ルール | | §13 |
| ルールタグ | | ルール適用のためのタグ（§14） |
| 派生ルール参照 | | この業務で有効な派生ルール（§10） |
| 作成日時・更新日時・作成者 | ✓ | |

### 7-5. STEP と業務部品

STEPは**再利用可能な業務部品**を配置したものとして定義 **MUST**。

初期に用意する業務部品：

| 部品 | 用途 |
|---|---|
| 入力 | 自由入力・数値・日付などの項目入力 |
| 選択 | 選択肢からの単一／複数選択 |
| チェック | チェックリストの消化 |
| 企業検索 | 条件による企業候補の検索（§17） |
| 企業選定 | 候補からの選定と理由記録（§17） |
| 顧客情報表示 | 顧客・案件情報の参照 |
| メール作成 | テンプレート差し込みとメール作成（§19） |
| 文章作成 | 定型文書の作成（§18） |
| 資料作成 | 提案資料等の作成 |
| タスク作成 | フォロータスクの生成（§9） |
| Calendar登録 | 予定の登録（§21） |
| ナレッジ表示 | 参照資料の提示（§16） |
| AI処理 | AIによる補助処理（§20） |
| 承認 | 上長等による承認 |
| 条件分岐 | 条件による経路分岐 |
| 完了 | 業務の終了 |

**業務部品は将来追加できる構造 MUST。** 部品の追加は開発作業とし、
既存の業務フロー定義・実行データに影響を与えないこと。

STEPが持つ情報：

- タイトル・説明・**ガイダンス**（このSTEPで何をするかの説明文）
- 業務部品の種別と、その設定
- 入出力（業務の変数との接続）
- 必須／任意
- 担当者の決め方（実行者／ロール指定／固定）
- 期限ルール・想定所要時間
- 参照ナレッジ
- ルールタグ
- 派生トリガー
- 完了条件（部品標準の上書き）

### 7-6. STEP順序と条件分岐

- 業務フローは一本道とは限らず、**有向グラフ**として表現 **MUST**
- 分岐は「条件付きの接続」として表現する。同じSTEPから複数の接続がある場合、
  優先順位順に条件を評価し、最初に成立したものへ遷移 **MUST**
- 条件が成立する接続が複数ある構成（並列）を許容 **MUST**
- 条件式は**データとして保存・編集可能**であること **MUST**（画面から編集できること）
- 循環経路を作れてはならない。定義保存時に検出して拒否 **MUST**

条件で参照できる値：

- 業務の変数（ヒアリング結果、選定サービス等）
- 各STEPの出力
- 対象エンティティの属性（顧客の業種、企業規模等）
- 現在日時

### 7-7. 完了条件

| レベル | 規則 |
|---|---|
| STEP | 部品ごとの標準完了条件、または定義で上書きした条件を満たすこと |
| 業務 | 必須STEPがすべて完了、かつ業務の完了条件式が成立すること |

完了条件を満たさない場合、**何が不足しているかを具体的に提示 MUST**（§27-3）。

### 7-8. 初期に実装するデモ業務

| # | 業務 | STEP |
|---|---|---|
| 1 | 新規問い合わせ | 問い合わせ → 顧客情報確認 → ヒアリング → サービス選定 → メール作成 → タスク作成 → 完了 |
| 2 | CV後対応 | CV → お礼メール → 資料送付 → フォロー日設定 → Calendar登録 → 完了 |
| 3 | 企業リサーチ | 条件入力 → 企業検索 → 候補表示 → **人間による選定** → 企業登録 → メール作成 → タスク作成 → 完了 |

これらは**シードデータとして投入**され、コードに埋め込まれてはならない **MUST NOT**。

### 7-9. 受け入れ基準

- [ ] デモ3業務が最初から最後まで実行できる
- [ ] 業務名・STEP名・分岐条件がコード内に文字列として存在しない
- [ ] 管理画面から新しい業務フローを追加でき、追加後すぐ実行できる
- [ ] 進行中の業務がある状態でその定義を編集しても、進行中の業務が壊れない

## 8. アドホック業務

### 8-1. 目的

定型業務として定義されていない突発的な業務を、その場で構造化して実行可能にする。

### 8-2. 導線

全画面から常時アクセスできる `＋新しい業務` を配置 **MUST**。

### 8-3. 入力

ユーザーは**自然文**で業務を入力する。

例：
- 「展示会で集めた企業から、営業できそうな会社を20社選んで」
- 「○○業界に提案できそうな企業を調べて」
- 「来週までに提案資料を作って」

### 8-4. AIによる分解

入力を以下8項目に分解 **MUST**：

| # | 項目 | 説明 |
|---|---|---|
| 1 | ゴール | この業務が完了した状態 |
| 2 | 必要な作業 | 実行すべき作業の並び |
| 3 | 必要な情報 | 作業に必要な入力 |
| 4 | 不足情報 | 現時点で欠けている情報（§8-5） |
| 5 | 確認事項 | 上司・顧客等に確認すべきこと |
| 6 | 必要なツール | 使用する業務部品・外部連携 |
| 7 | 完遂条件 | 完了とみなす条件 |
| 8 | 期限 | ゴール期限と各作業の期限（§13で逆算） |

さらに、想定される**派生タスク**を提示 **SHOULD**。

### 8-5. 不足情報検出

業務完遂に必要な情報が不足している場合、**「不足情報があります」と明示 MUST**。

検出対象の例：提案先／提案サービス／目的／期限／対象者／予算／担当者

不足情報の検出は、AIが停止していても**完了条件から機械的に導出できる範囲は必ず動作 MUST**（§20-4）。

### 8-6. 確認事項の生成

不足情報に対し `確認事項を作成` ボタンを提供 **MUST**。
押下するとAIが上司・顧客などに確認するための文章を生成する。
**生成された文章はユーザーが確認・編集してから使用する MUST**（送信の自動実行は禁止）。

### 8-7. ユーザー確認ゲート

> **AIの提案をそのまま実行しては MUST NOT。**

分解結果は**編集可能な形式**で提示し、ユーザーが以下を行えること **MUST**：

- 各作業の追加・削除・並べ替え・文言修正
- 期限の変更
- 派生タスクの採否選択
- 不要な項目の除外

ユーザーが `この内容で開始` を押して初めて業務実行が生成される **MUST**。

### 8-8. 定型業務への昇格

実行したアドホック業務を、業務フロー定義の**下書きとして保存**できること **SHOULD**。
繰り返し発生する業務を定型化する導線とする。

### 8-9. 受け入れ基準

- [ ] 「展示会で集めた企業から営業できそうな企業を20社選定して」が業務として起動する
- [ ] 分解結果を編集してから開始できる
- [ ] 開始前に不足情報が提示され、確認事項の文面を生成できる
- [ ] AIが応答しない状況でも、手動入力でアドホック業務を作成できる

## 9. タスク

### 9-1. 位置づけ

> **一般的なTodoリストではなく、「業務フローと紐付いたタスク」として設計 MUST。**

### 9-2. タスクが持つ情報

| 項目 | 説明 |
|---|---|
| タイトル・説明 | |
| ステータス | 未着手／進行中／ブロック中／承認待ち／完了／中止 |
| 優先度 | 低／通常／高／緊急 |
| 担当者 | |
| 期限・想定所要時間 | |
| **紐付く業務・STEP** | どの業務のどのSTEP由来か |
| **開始可能な業務フロー** | このタスクから起動できる業務（§9-4） |
| **親タスク** | 階層構造 |
| **派生元** | 派生の起点となった変更イベント（§10） |
| **派生ルール** | どのルールで生成されたか |
| **発生源** | 手動／業務フロー／派生／AI／スケジュール |
| **承認状態** | 確定済み／提案中／却下（§9-3） |
| 依存関係 | 先行タスク・後続タスク（§11） |
| カレンダー連携 | 登録済み予定への参照（§21） |

### 9-3. 承認状態（提案中タスク）

自動生成・AI生成されたタスクは **`提案中` 状態で作成 MUST**。
ユーザーが確認して確定するまで、通常のタスクとしては扱わない。

- 一覧では `提案中` を視覚的に区別 **MUST**
- 一括での採否操作を提供 **MUST**
- 却下されたタスクは履歴として残す **SHOULD**

### 9-4. タスクから業務を開始

タスクから `業務を開始` すると、該当する業務フローの実行が生成され、
業務ナビゲーターが開く **MUST**。開始された業務とタスクは相互に紐付ける。

### 9-5. 一覧のビュー

以下の切り替えを提供 **MUST**：今日／今週／期限超過／業務別／派生別／担当者別／提案中

### 9-6. 受け入れ基準

- [ ] 各タスクからその由来（業務・STEP・派生元）をたどれる
- [ ] タスクから業務を開始でき、業務ナビゲーターが開く
- [ ] 自動生成タスクが `提案中` として区別表示される

## 10. 派生タスク

### 10-1. 前提となる考え方

> **業務は一本道ではない。途中の条件変更や判断によって別タスクが発生する。**

この「変更による影響」を管理できることが、本プロダクトの中核価値の一つです。

### 10-2. 代表シナリオ

「キャンペーン終了日を **9/30 → 10/15** に変更」した場合：

| 影響区分 | 発生するタスク |
|---|---|
| 直接影響 | 配信設定変更／LP掲載期間変更 |
| 間接影響 | 案内メール内容確認／営業資料確認／関係者への通知 |
| 確認事項 | 契約期間との整合確認 |

### 10-3. 派生の起点

**すべての変更を「変更イベント」として記録 MUST。** 派生タスクの生成はこのイベントを唯一の入力とする。

記録する情報：対象エンティティ／対象項目／変更前の値／変更後の値／変更理由／実行者／発生日時／関連業務

### 10-4. 派生ルール

派生は**データとして定義されたルール**により決定 **MUST**（ハードコード禁止）。

派生ルールが持つ情報：

| 項目 | 説明 |
|---|---|
| 名称・有効/無効・優先順位 | |
| **トリガー** | 対象エンティティ／対象項目／変更種別／追加条件 |
| **適用範囲** | 対象業務・対象チーム（必須。無制限のルールは作れない） |
| **効果** | 生成するタスクのテンプレート群、または確認事項 |
| 効果ごとの影響区分 | 直接／間接／確認事項 |
| タスクテンプレート | タイトル／担当ロール／期限規則／依存関係／開始可能な業務フロー |
| AI補完の有無 | 漏れている派生の候補をAIに追加提案させるか |

### 10-5. 生成フロー

```
1. ユーザーが値を変更（9/30 → 10/15）
2. 変更イベントを記録
3. 派生ルールのトリガーを機械的にマッチング          ← 決定的処理
4. 効果からタスク草案を生成                          ← 決定的処理
5.（任意）AIが漏れている派生候補を追加提案           ← 補助
6. すべて「提案中」状態で保存                        ← MUST
7. ★ 確認画面：ユーザーが取捨選択・編集・期限調整
8. 確定 → 依存関係を張り、逆算スケジューラで期限確定（§13）
9. インパクトマップに反映（§12）
```

### 10-6. 確認ゲート

> **派生タスクを自動確定しては MUST NOT。必ず「提案中」を経由する。**

確認画面では以下を可能とする **MUST**：個別の採否／文言編集／担当者変更／期限変更／一括除外

### 10-7. AIの役割の限定

- 骨格（どの変更が何に影響するか）は**決定的な派生ルール**が決める
- AIは「他に漏れている派生はないか」の**候補追加のみ**を担当する
- **AIが停止していても、派生ルールによる生成は動作 MUST**

### 10-8. 系譜の追跡

各派生タスクから、その発生源をたどれること **MUST**：
どの変更イベントから／どの派生ルールで／どの親タスクの下に生成されたか。

### 10-9. 受け入れ基準

- [ ] 「キャンペーン終了日 9/30→10/15」で5つの派生タスクと1つの確認事項が提案される
- [ ] 提案は確定前にユーザーが編集・除外できる
- [ ] 各派生タスクから変更イベントをたどれる
- [ ] 新しい派生ルールをコード変更なしに追加できる

## 11. 業務間の依存関係

### 11-1. 依存の種類

| 種類 | 説明 |
|---|---|
| タスク間依存 | タスクAが完了しないとタスクBを開始できない |
| STEP間依存 | 業務フロー内の順序・分岐（§7-6） |
| 業務間依存 | 業務Aの完了が業務Bの前提となる |
| 情報依存 | あるタスクの出力が別タスクの入力になる |

### 11-2. 依存関係が持つ情報

先行／後続／依存種別（完了後開始 等）／遅延日数（先行完了からn日後に開始可能）

### 11-3. 挙動

- 先行タスクが未完了の後続タスクは **`ブロック中`** として表示 **MUST**
- 先行タスクの期限が変更されたら、後続タスクの期限を**再計算して提案 MUST**（自動確定はしない）
- 先行タスクが中止された場合、後続タスクの扱いをユーザーに確認 **MUST**

### 11-4. 循環の禁止

依存関係に循環を作れてはならない。登録時に検出して拒否 **MUST**。
既存データに循環が見つかった場合は、該当箇所を画面上で明示 **MUST**（§27-5）。

### 11-5. 受け入れ基準

- [ ] 依存のある派生タスクが正しくブロック表示される
- [ ] 循環する依存を登録しようとすると拒否され、どこが循環か示される
- [ ] 先行タスクの期限変更時に後続の期限変更が提案される

## 12. インパクトマップ

### 12-1. 目的

業務変更による影響範囲を**グラフィカルに可視化**し、見落としをなくす。

### 12-2. 構造

変更を起点とした3層構造で表示 **MUST**：

```
        ［ キャンペーン終了日 9/30 → 10/15 ］
                      │
     ┌────────────────┼────────────────┐
  直接影響          間接影響          確認事項
  ・配信設定        ・案内メール      ・契約期間との整合
  ・LP              ・営業資料
                    ・広告
```

| 層 | 定義 |
|---|---|
| 直接影響 | 変更対象に直結して対応が必要なもの |
| 間接影響 | 直接影響の結果として対応が必要になるもの |
| 確認事項 | 対応の要否を判断するために確認が必要なもの |

### 12-3. ノードが持つ情報

ラベル／影響区分／起点からの距離／対応タスクへの参照／対応状況（未対応・対応中・完了）／担当者

### 12-4. 操作

| 操作 | 挙動 |
|---|---|
| ノード選択 | 対応タスクの詳細を表示 |
| タスク化 | 未タスク化のノードからタスクを生成（提案中状態） |
| 影響外とする | 理由を記録して除外 |
| 一括タスク化 | 未対応ノードをまとめてタスク化（確認画面経由） |

### 12-5. 表示規則

- 未対応ノードを視覚的に強調 **MUST**
- 対応完了ノードは沈静化させる **SHOULD**
- 影響が0件の変更ではインパクトマップを表示しない（ノイズを出さない）**SHOULD**

### 12-6. 受け入れ基準

- [ ] 代表シナリオで3層が正しく描画される
- [ ] 未対応の影響が一目で分かる
- [ ] ノードからタスクを生成できる

## 13. 逆算スケジューラー

### 13-1. 目的

ゴールの期限から必要な作業の期限を逆算し、間に合う計画を提示する。

### 13-2. 動作例

```
ゴール：9/30 キャンペーン終了
      ↓ 逆算
9/29  最終確認
9/25  配信設定
9/22  メール確定
9/20  文章作成
```

### 13-3. 入力

ゴール期限／対象タスク群（依存関係を含む）／各タスクの想定所要時間／期限ルール／営業日設定

### 13-4. 期限ルールの表現

期限は**データとして定義 MUST**。以下を表現できること：

| 種類 | 例 |
|---|---|
| ゴールからの相対 | ゴールの10営業日前 |
| 先行タスクからの相対 | 先行完了の2日後 |
| 業務開始からの相対 | 開始から24時間以内 |
| 絶対日時 | 9/25 18:00 |

営業日のみで計算するか暦日かを指定できること **MUST**（日本の祝日を考慮 **SHOULD**）。

### 13-5. 計算方針

1. 依存関係を解析し、実行可能な順序を決定する
2. ゴールから遡って各タスクの最遅開始日・期限を算出する
3. 営業日設定を適用する
4. **循環がある場合は計算せず、循環箇所を明示 MUST**

### 13-6. 警告

以下を検出して警告 **MUST**：

- 逆算の結果、開始日が**過去**になる（既に間に合わない）
- 特定日に作業が過度に集中している
- 担当者の負荷が特定期間に集中している **SHOULD**
- 依存の先行タスクの期限が後続より遅い（矛盾）

### 13-7. 確定は人間が行う

**逆算結果は「提案」であり、自動確定しては MUST NOT。**
ユーザーが確認し、個別に調整してから確定する。

### 13-8. 再計算

ゴール期限が変更された場合、関連タスクの期限を再計算して**提案 MUST**（§11-3と同様、自動確定しない）。

### 13-9. 受け入れ基準

- [ ] ゴール期限を設定すると各タスクの期限案が提示される
- [ ] 営業日設定が反映される
- [ ] 間に合わない場合に警告が出る
- [ ] 代表シナリオ（10/15から逆算）で妥当な日程が提示される

## 14. 一時ルール／期間限定ルール

### 14-1. 目的

「今月だけ」「この案件だけ」といった一時的な取り決めを、**ユーザーが覚えていなくても業務に反映される**状態にする。

### 14-2. 代表シナリオ

```
「9月限定ルール」
対象：新規問い合わせ
内容：
  ・予算を確認
  ・導入時期を確認
  ・AI導入経験を確認
期間：9/1 〜 9/30
```

このルールが、新規問い合わせ業務のヒアリングSTEPに**自動的に表示・反映**されること **MUST**。

### 14-3. ルールが持つ情報

| 項目 | 必須 | 説明 |
|---|---|---|
| 名前 | ✓ | |
| 内容（説明） | ✓ | 人間が読むための説明 |
| 種別 | ✓ | 個別案件／期間限定／部署／標準（§14-6） |
| **対象業務** | ✓ | 対象となる業務・STEP・業務部品の種別 |
| **開始日** | ✓ | |
| **終了日** | 期間限定は✓ | |
| 優先順位 | ✓ | §14-6 |
| 適用条件 | | 追加の成立条件（顧客業種が○○の場合 等） |
| 有効／無効 | ✓ | 手動での有効化・無効化 |
| **効果** | ✓ | §14-4 |
| 作成者・作成日時 | ✓ | |

### 14-4. 効果の種類

ルールは業務フロー定義を**書き換えず**、表示時に**重ねて適用**する **MUST**。

| 効果 | 内容 |
|---|---|
| チェック項目を追加 | STEPに確認項目を追加する |
| 入力項目を追加 | フォームに項目を追加する |
| 確認を必須化 | STEP完了前に確認を挟む |
| テンプレートを差し替え | メール・文書テンプレートを変更する |
| STEPを挿入 | 指定STEPの前後にSTEPを追加する |
| 期限ルールを変更 | 期限の計算規則を上書きする |
| ナレッジを追加 | 参照資料を追加する |
| 注意文を表示 | 注意喚起を表示する |
| 完了をブロック | 条件未達なら完了させない |

### 14-5. 自動無効化

> **期間終了後は自動的に無効化 MUST。**

- 有効判定は「現在日時が開始日〜終了日の範囲内、かつ有効フラグが立っている」こと
- **期限切れルールを無効化するための定期処理・手動操作を必要としては MUST NOT**
- 開始日が未来のルールは「予約」として登録でき、開始日に自動的に効き始める **MUST**

### 14-6. ルールの優先順位

競合する場合は以下の優先順位で処理 **MUST**：

```
1. 個別案件ルール      ← 最優先
2. 期間限定ルール
3. 部署ルール
4. 標準業務フロー      ← 最も弱い
```

同一種別内では設定された優先順位の数値、それも同じ場合は作成日時の新しい方を優先 **MUST**。

### 14-7. 競合の警告

高い優先順位のルールが勝つが、**重要な競合が発生した場合はユーザーに警告 MUST**。

競合の例：
- 複数のルールが同じ項目に異なる値を設定している
- 高優先ルールが低優先ルールの必須項目を打ち消している
- 期限ルールが二重に上書きされている

警告は業務ナビゲーターの上部に表示し、「どのルールがどのルールを上書きしたか」を示す **MUST**。

### 14-8. ルール作成時のプレビュー

ルールを保存する前に、**適用結果をプレビュー MUST**。

```
このルールは以下に影響します：
  ・「新規問い合わせ」の STEP2「ヒアリング」に確認項目を3件追加
  ・適用期間：2025/9/1 〜 2025/9/30（残り 33日）
  ・影響を受ける進行中の業務：4件
```

### 14-9. 適用の追跡

STEPを完了した時点で「どのルールが適用された状態で完了したか」を記録 **MUST**。
事後に「なぜこの項目が表示されていたのか」を追跡できること。

### 14-10. 受け入れ基準

- [ ] 「9月限定ルール」を登録すると、新規問い合わせのヒアリングSTEPに3項目が自動追加される
- [ ] 10/1になると、定期処理なしで自動的に表示されなくなる
- [ ] 保存前にプレビューで影響範囲が分かる
- [ ] ルールを削除しても業務フロー定義が変化していない
- [ ] 競合するルールを登録すると警告が表示される

## 15. 業務コンテキスト

### 15-1. 定義

**業務コンテキスト**とは、「今この瞬間、この業務のこのSTEPで、ユーザーが知っている必要があることの集合」です。

### 15-2. 構成要素

| 要素 | 内容 |
|---|---|
| 関連ルール | このSTEPに適用されているルール（§14） |
| 関連ナレッジ | このSTEPで参照すべき資料（§16） |
| 不足情報 | 完了に必要だが未充足の項目 |
| 派生タスク | この業務・STEP由来の派生タスク（§10） |
| 期限 | このSTEPと業務全体の期限、残り時間 |
| 必要ツール | このSTEPが使用する外部連携（§21・§22） |
| 対象情報 | 顧客・企業・案件などの対象データ |

### 15-3. 決定規則

業務コンテキストは§5-1のスコープ規則により**機械的に決定 MUST**。
表示するかどうかを画面ごとに個別実装しては **MUST NOT**（規則を一箇所に集約する）。

### 15-4. 表示規則

- 常時表示するが、**空の要素は表示しない**（見出しだけ並べない）**MUST**
- 要素は§4-2の優先順位に従って並べる **MUST**
- 件数が多い場合は上位のみ表示し、残りは折りたたむ **SHOULD**
- 注意を要するもの（期限超過・未対応の不足情報・競合警告）は最上部に固定 **MUST**

### 15-5. 受け入れ基準

- [ ] STEPを進めるとコンテキストパネルの内容が切り替わる
- [ ] 無関係なルール・ナレッジが表示されない
- [ ] 空のセクションが表示されない

## 16. ナレッジ

### 16-1. 扱う情報

マニュアル／FAQ／社内ルール／過去資料／外部ストレージ上のファイル／外部ドキュメントツールのページ

### 16-2. 最重要方針

> **ナレッジ検索画面を中心にしては MUST NOT。**
> ナレッジは「業務STEPから必要なものが提示される」ことを主導線とする。

検索画面は存在してよいが、それは取りこぼしを拾うための補助手段です（§5・原則2）。

### 16-3. ナレッジが持つ情報

タイトル／本文または外部リンク／出所（社内・外部ストレージ・外部ドキュメント）／種別（マニュアル・FAQ・ルール・資料）／タグ／**紐付くSTEP・業務**／更新日時／管理者

### 16-4. STEPへの紐付け

- 業務フロー定義のSTEPが、参照するナレッジを明示的に指定できる **MUST**
- 加えて、業務部品の種別・タグによる自動的な紐付けを行う **SHOULD**
- 業務中は§5-1のスコープ規則で絞り込んで表示 **MUST**

### 16-5. 鮮度管理

- 更新日時を表示 **MUST**
- 一定期間更新されていないナレッジに注意表示を出す **SHOULD**
- 参照されなかったナレッジ／頻繁に参照されたナレッジを管理者が把握できる **SHOULD**

### 16-6. 外部連携（将来）

外部ストレージ・外部ドキュメントツール上のファイルを、**メタデータとして取り込み**、
本文は元の場所を参照する方式とする **SHOULD**（§22）。

### 16-7. 受け入れ基準

- [ ] STEPを開くと、そのSTEPに必要な資料が既に画面上にある
- [ ] ナレッジを見るために検索する必要がない
- [ ] 管理者がナレッジをSTEPに紐付けられる

## 17. 企業検索／企業選定

### 17-1. 目的

提案・営業対象となる企業を条件から絞り込み、**人間が納得して選定できる**状態にする。

### 17-2. 検索条件

| 条件 | 必須 |
|---|---|
| 業界 | |
| 従業員規模 | |
| 地域 | |
| 売上 | |
| AI導入状況 | |
| 任意条件（自由文） | |

条件は保存・再利用できる **SHOULD**。

### 17-3. 候補一覧の操作

| 操作 | 内容 |
|---|---|
| 選択 | 候補を選定対象に加える |
| 除外 | 候補から外す（理由を記録できる） |
| 比較 | 複数候補を並べて比較する |
| 詳細確認 | 企業の詳細情報を表示する |
| 選定理由 | **選定した理由を記録する（§17-5）** |

### 17-4. AIの役割

AIは以下を**支援**する：候補の整理・要約／比較軸の提示／条件との適合度の説明／優先度の提案

> **最終選定は人間が行う MUST。AIが選定を確定しては MUST NOT。**

### 17-5. 選定理由の記録

選定・除外の理由を記録できること **MUST**。
これは後から「なぜこの企業を選んだのか」を説明でき、ナレッジとして蓄積するためです。

### 17-6. 選定結果の受け渡し

選定結果は業務の変数として後続STEPに引き渡される **MUST**
（例：選定企業 → メール作成STEPの宛先・差し込み情報）。

### 17-7. データソース

初期は社内に保持する企業データを対象とする。
将来的に外部の企業検索サービスへ接続できる構造とする **MUST**（§20-5）。

### 17-8. 受け入れ基準

- [ ] 条件を指定して候補が一覧表示される
- [ ] 選択・除外・比較・詳細確認・理由記録ができる
- [ ] AIの提案だけでは選定が確定しない
- [ ] 選定結果が後続STEPに引き渡される

## 19. メール作成

### 19-1. メールフォーマット（FMT）管理

メールFMTを**データとして管理 MUST**。管理者が追加・編集できること。

初期に用意するFMTの例：CV後お礼／新規問い合わせ返信／展示会フォロー／アポイント依頼

### 19-2. FMTが持つ情報

名称／件名／本文／差し込み変数の定義／紐付く業務・STEP／トーン

### 19-3. 差し込み

企業情報・顧客情報・業務の変数を**自動差し込み MUST**。

差し込み値が欠損している場合、**送信前に明示 MUST**（§27-3）。
欠損したまま送信できては **MUST NOT**。

### 19-4. AI補助

- 本文の生成・推敲・トーン調整を提供 **SHOULD**
- **AIの提案は元の文面との差分が分かる形で提示 SHOULD**
- **送信前に必ずユーザーの確認を required MUST**

### 19-5. 送信

| 段階 | 挙動 |
|---|---|
| 初期 | 下書きとして保存。実際の送信は行わない |
| 将来 | 外部メールサービスへ下書き作成、または送信（§22） |

> **AIがメールを自動送信しては MUST NOT。** いかなる将来拡張でもこの制約を維持する。

### 19-6. 受け入れ基準

- [ ] STEPからFMTが提示され、差し込みが行われる
- [ ] 差し込み欠損が送信前に検出・表示される
- [ ] AI推敲を使っても、ユーザー確認なしに確定しない
- [ ] 管理者がFMTを追加できる

## 20. AIツール連携

### 20-1. AIの位置づけ

> **AIは主役ではない。骨格は決定的なロジックが作り、AIはその周辺を補助する。**

### 20-2. AIを利用する箇所

| # | 用途 | ユーザー確認 |
|---|---|---|
| 1 | 業務分解（アドホック業務） | **必須** |
| 2 | 不足情報検出 | **必須** |
| 3 | 確認事項の文章生成 | **必須**（使用前） |
| 4 | 文章生成・推敲 | **必須**（確定前） |
| 5 | メール文面の生成・推敲 | **必須**（送信前） |
| 6 | 企業情報の整理・要約 | 参考表示 |
| 7 | 検索結果の整理・絞り込み提案 | **選定は人間のみ** |
| 8 | 派生タスク候補の追加提案 | **必須** |
| 9 | 変更影響の分析 | **必須** |
| 10 | 業務フロー作成支援 | **必須**（下書き保存） |

### 20-3. 確認ゲート（最重要制約）

> **重要な処理をAIが勝手に確定しては MUST NOT。**

以下は**必ずユーザーの明示的な確認を経る MUST**：

- 業務の開始
- タスクの確定
- 派生タスクの確定
- メールの送信
- 文書の確定
- 企業の選定
- 業務フロー定義の公開
- 期限の確定

AIの提案はすべて「提案」として記録し、採用・編集・却下の結果を保持する **MUST**。

### 20-4. AIが利用できない場合の挙動

> **AIが停止していても、プラットフォームの中核機能は動作 MUST。**

| 機能 | AI停止時の代替 |
|---|---|
| 業務フロー実行 | 影響なし（AIに依存しない） |
| 派生タスク生成 | 派生ルールによる決定的生成のみ動作 |
| 不足情報検出 | 完了条件からの機械的導出のみ動作 |
| 逆算スケジュール | 影響なし（AIに依存しない） |
| ルール適用 | 影響なし（AIに依存しない） |
| 文章・メール生成 | テンプレートをそのまま使用 |
| 業務分解 | 手動入力で作成 |

AI機能が利用不可の場合、**その旨を明示し、代替手段を提示 MUST**（§27-2）。

### 20-5. 拡張性

AI提供事業者・モデルを差し替えられる構造とする **MUST**。
特定の事業者・モデルに業務ロジックが依存しては **MUST NOT**。

### 20-6. 受け入れ基準

- [ ] 主要12画面にAIチャットが主役として存在しない
- [ ] §20-3の各操作でユーザー確認を経ずに確定できない
- [ ] AI連携を無効にしても、業務フロー実行・派生タスク生成・逆算が動作する

## 21. Google Calendar連携

### 21-1. 目的

業務の期限・タスク・予定をカレンダー上でも把握できるようにする。

### 21-2. 対象

| 対象 | 登録内容 |
|---|---|
| タスク | 期限を予定として登録 |
| 業務の期限 | 業務全体の締切 |
| フォロー予定 | 業務フローで設定したフォロー日 |
| 会議・商談 | ユーザーが登録する予定 |

### 21-3. 業務フローからの登録

業務フローのSTEPに「Calendar登録」部品を配置でき、STEP実行時に予定を登録できる **MUST**。
登録内容（タイトル・日時・参加者・説明）は業務の変数から組み立てる。

### 21-4. 同期方針

|---|---|
| 初期 | システム内で予定を管理。外部連携は行わない |

登録した予定への参照を保持し、後から更新・削除できる **MUST**。

### 21-5. 連携失敗時

カレンダー登録に失敗しても、**業務の進行を妨げては MUST NOT**。
失敗を記録し、後から再試行できること **MUST**（§27-2）。

### 21-6. 受け入れ基準

- [ ] 業務フローからカレンダー登録STEPを設定できる
- [ ] 登録した予定とタスクが相互に紐付く
- [ ] 連携失敗時も業務を継続でき、再試行できる

## 24. データモデル

本章は**概念モデル**を定めます。物理設計は `docs/DESIGN.md` を参照してください。

### 24-1. 中核となる分離

| 概念 | 役割 | 変更の影響 |
|---|---|---|
| **業務フロー定義** | 手順のテンプレート（設計図） | 編集しても進行中の業務に影響しない |
| **業務実行** | 進行中／完了した個々の業務（実体） | 開始時の定義バージョンを固定して保持 |

### 24-2. 主要エンティティ

| エンティティ | 責務 |
|---|---|
| **業務フロー定義** | 業務の手順テンプレート。バージョンを持つ（§7-4） |
| **STEP定義** | 業務部品を配置した1手順（§7-5） |
| **STEP接続** | STEP間の順序と条件分岐（§7-6） |
| **業務実行** | 進行中の業務1件。現在STEP・変数・期限・担当者を保持 |
| **STEP実行** | 業務実行内の1STEPの状態・出力・適用ルール |
| **業務イベント** | 業務中に起きたすべての変化の記録（追記専用） |
| **変更イベント** | 値の変更（変更前・変更後・理由）。派生の起点（§10-3） |
| **タスク** | 業務・STEPと紐付くタスク（§9-2） |
| **タスク依存** | タスク間の依存関係（§11-2） |
| **派生ルール** | 変更から派生タスクを生成する規則（§10-4） |
| **業務ルール** | 一時ルール・部署ルール等（§14-3） |
| **影響グラフ** | 変更イベントを起点とする影響の構造（§12-2） |
| **ナレッジ** | 参照資料（§16-3） |
| **メールFMT／文書テンプレート** | 差し込み可能な雛形（§18-3・§19-2） |
| **企業／企業候補／選定結果** | 企業検索・選定の対象と結果（§17） |
| **顧客／担当者／案件** | 業務の対象となる相手 |
| **カレンダー連携** | 外部予定への参照（§21-4） |
| **AI提案** | AIの提案と、その採否の結果（§20-3） |
| **ユーザー／チーム／ロール** | 権限と担当（§23） |

### 24-3. 設計制約

以下は仕様上の制約であり、実装がこれを満たさない場合は仕様違反です。

1. **業務フロー・STEP・条件・ルール・派生・期限・依存関係は、すべてデータとして表現 MUST**
2. **業務実行は開始時の定義バージョンを保持 MUST**
3. **すべての状態変化はイベントとして記録 MUST**（派生・影響分析・監査の共通の入力とする）
4. **ルールは定義を書き換えず、表示時に重ねて適用 MUST**
5. **条件式はデータとして保存・編集可能 MUST**（実行可能なコード片として保存しない）
6. **自動生成された提案は、確定状態と区別して保持 MUST**
7. **削除は原則として論理削除 SHOULD**（履歴と追跡可能性を保つ）

### 24-4. 受け入れ基準

- [ ] 業務名・STEP名・分岐条件・ルール内容がコード内に文字列として存在しない

## 26. UI/UXルール

### 26-1. 禁止事項

| # | 禁止 | 理由 |
|---|---|---|
| 1 | AIチャット画面をメインUIにする | §1-2 |
| 2 | 全ルール・全ナレッジを業務中に一覧表示する | §5・原則3 |
| 3 | ユーザーに機能を選ばせる導線を主導線にする | §4-1 |
| 4 | AIの出力を確認なしに確定する | §20-3 |
| 5 | 情報を見るために業務から離脱させる | §5・原則4 |
| 6 | 空のセクションの見出しだけを表示する | §15-4 |
| 7 | 何が足りないか示さずに操作をブロックする | §27-3 |

### 26-2. 必須事項

| # | 必須 |
|---|---|
| 1 | どの画面でも「今どこにいるか」が分かる |
| 2 | 次のアクションが1つのボタンとして明示されている |
| 3 | 期限は常に「日付」と「残り時間」の両方を示す |
| 4 | 期限超過・未対応の不足情報・ルール競合は最上部に表示する |
| 5 | 自動生成・AI生成のものは、確定済みのものと視覚的に区別する |
| 6 | 破壊的操作（業務の中止・ルールの削除・定義の公開）は確認を挟む |
| 7 | 中断した業務は、離脱時の状態で再開できる |

### 26-3. 情報密度

- 1画面で扱う主要な意思決定は**1つ**に絞る **SHOULD**
- 現在STEPの領域が画面内で最大面積を占める **MUST**
- 補助情報は現在STEPより視覚的に弱くする **MUST**

### 26-4. 状態の表現

| 状態 | 表現方針 |
|---|---|
| 完了 | 沈静化させる（強調しない） |
| 進行中 | 最も強調する |
| 未着手 | 中間的な強度 |
| ブロック | 理由とともに明示する |
| 提案中 | 確定済みと明確に区別する |
| 期限超過 | 警告色で最上位に表示する |

### 26-5. 用語

画面上の用語は統一 **MUST**。実装上の名称ではなく、**ユーザーが認識する言葉**を使う。

| 使う | 使わない |
|---|---|
| 業務 | ワークフロー実行、ラン |
| 手順・STEP | ノード、ステート |
| 一時ルール | オーバーレイ、パッチ |
| 派生タスク | デリバティブタスク |
| 提案中 | pending、draft |

### 26-6. アクセシビリティ

- キーボードのみで主要導線を完遂できる **SHOULD**
- 状態を色のみで表現しない（記号・文言を併用）**MUST**
- 主要な操作にフォーカス表示がある **MUST**

## 27. エラー時の挙動

### 27-1. 基本原則

> **業務を止めない。何が起きたか・次に何をすればよいかを必ず示す。**

エラー表示は以下3点を必ず含む **MUST**：

1. 何が起きたか（技術用語を使わない）
2. なぜ起きたか（分かる範囲で）
3. **ユーザーが次に取れる行動**

「エラーが発生しました」だけの表示は **MUST NOT**。

### 27-2. 外部連携の失敗

| 対象 | 挙動 |
|---|---|
| カレンダー登録 | 業務は継続。失敗を記録し、再試行導線を提示 **MUST** |
| メール送信・下書き作成 | 業務は継続。内容を保持し、再試行導線を提示 **MUST** |
| 外部ストレージ取得 | 該当ナレッジのみ利用不可と表示。他は通常動作 **MUST** |
| 企業検索API | 検索のみ失敗と表示。手動入力・既存データでの続行を可能にする **MUST** |
| AI呼び出し | §27-4 |

**外部連携の失敗を業務の失敗として扱っては MUST NOT。**

### 27-3. 入力・完了条件の不足

- 何が不足しているかを**項目名で具体的に提示 MUST**
- 不足項目への導線（そこへジャンプする操作）を提供 **MUST**
- 「保存できません」だけの表示は **MUST NOT**

表示例：
```
このSTEPを完了できません
  ・「予算」が未入力です（9月限定ルールにより必須）  → 入力する
  ・「導入時期」が未入力です（9月限定ルールにより必須）→ 入力する
```

### 27-4. AI処理の失敗

| 状況 | 挙動 |
|---|---|
| 応答が得られない | AI補助が利用できない旨を表示し、**手動での代替手段を提示 MUST** |
| 応答が想定形式でない | 提案として採用せず、再試行または手動入力を促す **MUST** |
| 応答が遅い | 処理中であることを示し、待たずに他の操作へ移れる **SHOULD** |

**AIの失敗によって業務の進行が不可能になっては MUST NOT**（§20-4）。

### 27-5. データの矛盾

| 状況 | 挙動 |
|---|---|
| 依存関係の循環 | 登録を拒否し、循環箇所を明示 **MUST**（§11-4） |
| ルールの競合 | 優先順位で解決しつつ、重要な競合は警告 **MUST**（§14-7） |
| 逆算で期限が過去になる | 計算は行い、間に合わない旨を警告 **MUST**（§13-6） |
| 参照先の欠損（削除された顧客等） | 業務は継続。欠損を明示し、再指定を促す **MUST** |

### 27-6. 同時編集の競合

同じ業務・タスク・定義を複数ユーザーが同時に更新した場合：

- 後勝ちで**上書きしては MUST NOT**
- 競合を検出し、双方の内容を提示して解決させる **MUST**
- 業務フロー定義の場合、公開中バージョンは保護する **MUST**

### 27-7. データ消失の防止

- 業務実行中の入力は、STEP完了前でも保持する **MUST**
- 中断・ブラウザ終了・通信断からの復帰時に、入力内容を復元する **MUST**
- 破壊的操作の前に確認を挟む **MUST**（§26-2）

### 27-8. 受け入れ基準

- [ ] 外部連携をすべて無効にしても、業務の開始から完了まで到達できる
- [ ] AI連携を無効にしても、業務の開始から完了まで到達できる
- [ ] 完了条件未達のとき、不足項目が名前で表示され、そこへ移動できる
- [ ] 入力途中で離脱しても内容が失われない

## 28. 将来的な業務フロー追加方法

### 28-1. 前提

> **業務フローの追加・変更に、コードの変更・再デプロイを必要としては MUST NOT。**

### 28-2. 追加の導線

業務フロー一覧画面に `＋新しい業務フロー` を配置 **MUST**（業務設計者・管理者のみ）。

### 28-3. 設定できる項目

| 項目 | 必須 | 説明 |
|---|---|---|
| 業務名 | ✓ | |
| 業務説明 | ✓ | |
| 対象者 | | ロール・チーム |
| STEP | ✓ | 業務部品を選んで配置 |
| STEP順 | ✓ | 順序の指定 |
| 分岐 | | 条件付きの経路（§7-6） |
| 完了条件 | ✓ | |
| 使用部品 | ✓ | STEPごとの業務部品と設定 |
| メールFMT | | STEPで使用するFMT |
| ナレッジ | | STEPで提示する資料 |
| タスク生成ルール | | STEPで生成するタスク |
| 期限ルール | | 業務・STEPの期限規則 |
| ルールタグ | | 一時ルールを効かせるためのタグ |
| 派生トリガー | | このSTEPが発火しうる派生ルール |

### 28-4. コード変更が必要になる範囲

| 追加するもの | コード変更 |
|---|---|
| 業務フロー | **不要** |
| STEP | **不要** |
| 条件分岐 | **不要** |
| 一時ルール | **不要** |
| 派生ルール | **不要** |
| 期限ルール | **不要** |
| 依存関係 | **不要** |
| メールFMT・文書テンプレート | **不要** |
| ナレッジ | **不要** |
| **新しい業務部品そのもの** | 必要（開発作業） |
| **新しい外部連携** | 必要（開発作業） |

業務部品の追加は開発作業ですが、**既存の業務フロー定義・実行データに影響を与えては MUST NOT**。

### 28-5. 下書きと公開

| 状態 | 挙動 |
|---|---|
| 下書き | 編集中。実行できない。進行中の業務に影響しない |
| 公開 | 実行可能。以後の新規実行に適用される |
| アーカイブ | 新規実行不可。進行中・完了済みの業務は影響を受けない |

**公開時にバージョンを増加させ、進行中の業務は従前のバージョンで動作を継続 MUST**（§7-3）。

### 28-6. 保存時の検証

保存・公開時に以下を検証 **MUST**：

- 到達不能なSTEPが存在しないか
- 完了STEPへ到達できない経路が存在しないか
- 循環経路が存在しないか
- 参照している変数・ナレッジ・テンプレートが存在するか
- 必須設定が欠けている業務部品がないか

検証エラーは**該当STEPを画面上で明示 MUST**（§27-3）。

### 28-7. 動作確認

公開前に、**テスト実行**できること **SHOULD**。
実データを作らずにフローを一通り通し、分岐・ルール適用・タスク生成を確認できる。

### 28-8. AIによるフロー案生成（将来）

業務の説明を自然文で入力すると、AIが業務フローの**下書き**を生成する機能を将来追加できる構造とする **MUST**。

- 生成結果は必ず**下書き**として保存 **MUST**
- **AIが業務フローを公開しては MUST NOT**（§20-3）

### 28-9. 受け入れ基準

- [ ] 管理画面のみで新しい業務フローを追加し、実行できる
- [ ] STEPの追加・削除・並べ替え・分岐設定ができる
- [ ] 保存時に到達不能STEP・循環が検出される
- [ ] 公開しても進行中の業務が影響を受けない
- [ ] 上記のいずれにもコード変更・再デプロイが不要
